# Intervexa engineering status — October 10, 2026

This iteration extends the existing Next.js/FastAPI/SQLAlchemy application. Baseline before edits: 39 backend tests passed; TypeScript, ESLint and production build passed. Existing accounts and database architecture were preserved. Source is now published to the private [Lingu17/intervexa](https://github.com/Lingu17/intervexa) repository, GitHub Actions passed, and the frontend is deployed on Render Free at [intervexa-web.onrender.com](https://intervexa-web.onrender.com). The API is prepared but awaits the owner's database password entry in Render; account and repository workflows are not yet verified on the deployed site.

## Implemented

- Registration origin fix: exact localhost and 127.0.0.1 aliases at the configured development port. Production allows only explicit HTTPS origins. Missing origins, lookalike hosts, other ports and failed CSRF remain rejected. Personal Gmail/Outlook signup is tested; company-email framing was removed.
- Google/GitHub social authentication code: one-time cookie-bound expiring database state, provider identity verification, stable provider subject IDs and existing-session account linking. Google signature/issuer/audience/expiration/nonce/verified-email rejection tests use actual locally signed JWT fixtures. Email collisions cannot silently create or link an account. Provider tokens are not persisted. Live OAuth is unverified without client credentials.
- A larger, original living-code architecture component with repository core, services/files/API/database/function/PR/interface/test shapes, relationship edges, hover labels, selection, camera focus and details. Demand rendering limits GPU work. Keyboard DOM controls and a reduced-motion/WebGL/error SVG fallback preserve functionality. Authenticated explorer graphs consume indexed repository data; public examples are explicitly conceptual.
- Public product, repository intelligence, PR analysis, workflow, architecture, security, supported scope, pricing, docs, FAQ, contact, privacy, terms, acceptable use, support/status and recovery-status pages. Detailed homepage includes labeled interactive source comparison, data flow, manual-review comparison, independent developer use cases, FAQ, working contact and complete footer. Legal notices require deployment operator identity and review before a public launch.
- Purposeful disconnected-workspace onboarding, contextual repository navigation, command search, analysis filters, explicit PR selection, changed-file/diff impact views, source references, progress/recovery, findings, test logs, settings, profile and initials avatar, JSON export, confirmed account deletion and real usage/processing bounds. Workspace appearance persists in the database. Invitations and multi-workspace switching are not exposed.
- Authorized branch listing and bounded exact-commit repository indexing: 60 files, 50 KB/file, 500 KB source, 10,000 tree entries and a three-minute wall timeout. Python AST symbols and module-path import edges; searchable selected text languages; explicit omissions. Indexed source/file retrieval, filename/symbol/identifier search and source-grounded BYOK questions. AI answers with missing or nonexistent retrieved path/line citations are rejected; citation validity does not prove every interpretation.
- Explicitly approved OpenAI embeddings and cosine semantic search: 256 dimensions, first 20 indexed file excerpts of 3,000 characters. Keys are ephemeral; scoped vectors persist until refresh, expiry or removal. Index refresh invalidates old vectors. Questions currently use lexical retrieval; semantic retrieval has its own search mode within the same repository workflow.
- Existing pinned static PR analysis, persistent queue/retries/lease recovery, cancellation/staleness, Python contract comparison, reviewed test generation and separate rootless-Podman runner preserved. Manual selection supports 2–10 PRs; verification supports pairs sharing a base. Static hypotheses remain unverified until experimental evidence exists. GitHub Checks now require both explicit backend enablement and repository-policy opt-in, and stay advisory.
- Database-backed contact form: validation, honeypot, rate limiting, accurate commit-success/error states and 90-day cleanup. Email delivery and an admin review portal are unavailable; the UI says messages are recorded, not sent by email.
- Four Alembic revisions, including additive intelligence/auth/contact tables and a data-preserving provider-preference workspace migration. Real local database migrated to 0004_preferences. Upgrade/downgrade/reapply and model/schema comparison pass; a fixture confirms existing email/hash/model/token defaults survive the latest migration.

## External configuration and remaining limits

The owner-authorized GitHub sign-in client and repository App are created, with the App installed only on `Lingu17/intervexa`. Their credentials are in the prepared Render API form, together with the generated session secret and private-key secret file. The dedicated Supabase Free project is healthy and its public Data API is disabled. The frontend deployment succeeded and returned HTTP 200; GitHub Actions passed its full validation run. The API still awaits secure database password entry, so live OAuth, repository ingestion, webhook delivery, PostgreSQL migrations and HTTPS session workflows remain unverified. Google OAuth, AI keys and a dedicated Linux runner remain unconfigured. See [integration setup](integrations.md), [deployment](deployment.md) and [runner requirements](../runner/README.md).

This remains an early-access implementation, not a completed production SaaS. Email verification/recovery delivery, a distributed/proxy-aware limiter, operational backups/monitoring, independent security/legal review, resolved cross-language and dynamic dependency graphs, SQL migration semantics, higher-order combinations and private/dependency-installing/multi-framework runners remain unfinished. Password recovery is an honest unavailable state rather than a fake send operation. Contact review requires the deployment operator's database access; no dashboard is advertised.

Personal workspaces currently have one owner. Nonsecret AI preferences are scoped to that user and workspace; a future multi-workspace UI needs further schema/workspace-selection work. Account export contains the latest 500 retained analysis snapshots and their findings/tests, not every database record or backup. Retention cleanup depends on the API worker being awake. In-memory limits are per-process; local frontend proxy traffic shares loopback buckets.

Vercel Hobby is unsuitable for a commercial SaaS deployment. Render free services sleep and share hours; Supabase free storage and inactivity limits apply. These are evaluation choices, not availability guarantees. Sites cannot run the Python API/rootless Linux runner, so no disconnected static version was published.
